# Backlot 页面登录门禁设计

## 目标

未登录用户访问项目列表 `/` 或项目看板 `/p/<project-id>` 时，应先进入 `/login`，避免看到一个看似可用但无法读取数据的工作台外壳。登录后继续进入项目列表，现有“新建复刻项目”流程保持不变。

## 方案

在 `create_app` 中增加页面级会话检查，仅作用于 HTML 页面路由：

- `/`：无有效 `backlot_session` 时返回 303 到 `/login`。
- `/p/<project-id>` 以及 `/p/` 下的所有嵌套 HTML 路由：无有效会话时返回 303 到 `/login`。
- `/login`、静态 UI 资源、健康检查保持公开。
- `/api/*` 继续使用现有 `require_access` 和 401 JSON 响应，不改变 API 权限模型。
- 已登录用户访问 `/login` 时仍可看到登录页，避免引入额外的重定向状态。
- `auth_mode="test"` 保持现有免认证行为，避免改变共享测试客户端的契约；页面门禁只在生产认证模式启用。

## 数据流与错误处理

页面路由使用现有 `AuthStore.resolve_session` 检查 cookie；过期、撤销或缺失的 cookie 统一视为未登录。重定向使用 303，避免浏览器复用任何非 GET 方法。登录后的目标固定为 `/`，本次不引入 return-to 参数。

## 测试

新增页面路由测试覆盖：

- 未登录、会话过期、会话已撤销时，访问 `/`、`/p/<id>` 和 `/p/` 下的嵌套路由均得到 303，且 `Location: /login`；测试禁用自动跟随重定向。
- 有效会话访问 `/` 和 `/p/<id>` 得到工作台 HTML。
- `/api/projects` 未登录时仍返回 JSON `401`。
- `/login`、`/ui/*` 和 `/api/health` 保持公开。
- `auth_mode="test"` 的共享测试客户端仍可直接访问页面。
