# 视频审批工作台业务语言与批单串联设计

> 日期：2026-08-28
> 状态：待实施
> 范围：视频生成后的人审、批量比较、单条深入复核和统一提交
> 本轮不包含编辑工作室

## 1. 背景与目标

现在的系统已经能生成视频、保存阶段产物并提供批量候选，但一线人员需要在多个页面和技术字段之间来回判断。主要问题不是没有数据，而是：

- 批量工作台和单条审批台看起来像两套系统，进入单条后不知道怎样回到批量；
- 页面使用“stage、revision、runtime、creative lock”等内部词，一线人员不能直接判断要做什么；
- 视频、脚本、分镜、口播、字幕、评分和失败原因没有按生产顺序组织；
- 批量比较和单条审批缺少统一提交边界，容易重复审批或误把旧快照当成最新结果。

本设计把工作台收敛为一条主线：

```text
批量总览 → 比较候选 → 打开一条深入复核 → 返回批量 → 批量确认当前门 → 选择进入精剪 → 统一提交
```

目标是让一线人员在 5 秒内回答三件事：

1. 现在视频做到哪一步；
2. 这次需要我确认什么；
3. 我确认后系统会继续生成什么。

### 成功标准

1. 批量入口首屏同时显示批次进度、候选画面、候选结论和当前唯一主动作。
2. 从批量候选进入单条复核后，页面保留“来自哪个批次、返回批量”的上下文，关闭或完成复核不会丢失选择。
3. 单条复核展示视频和对应产物，不要求用户阅读 JSON、路径、模型名或内部阶段编号。
4. 三个生产确认点（脚本、素材、样片）都能在批量台聚合处理，也能在单条台单独处理；两种入口写入同一条审批事实。
5. 批量动作采用 all-or-nothing：任一候选快照过期、无权限或确认不完整，整批不提交部分结果。
6. 技术失败、产物缺失和报告不完整都保留在候选列表中，并明确说明下一步。

## 2. 业务主线

### 2.1 一线可读的九步流程

页面显示以下中文名称；括号内为代码阶段，仅供实现和日志使用，不出现在一线主界面。

| 顺序 | 页面名称 | 用户能看到的结果 | 是否需要人工确认 |
|---|---|---|---|
| 1 | 了解任务 | 参考片重点、现有素材、平台和时长要求 | 否，系统自动整理 |
| 2 | 看创意方案 | 3–5 个创意方向和每个方向的差异 | 否，进入脚本前自动采用已选方案 |
| 3 | 确认脚本 | 口播、屏幕文字、时长和卖点顺序 | 是，脚本确认 |
| 4 | 看分镜 | 每个镜头用哪段素材、展示什么动作、持续多久 | 否，作为下一步的可读产物 |
| 5 | 确认制作准备 | 口播、字幕、背景音乐、画面素材和预计费用 | 是，素材确认；确认前不调用付费生成 |
| 6 | 查看样片 | 可播放样片、五项效果检查、质量评分和风险 | 是，样片确认 |
| 7 | 等待精剪 | 从已通过样片中选出的 1–2 条进入精剪队列 | 否，本轮只提交选择结果，不开放编辑 |
| 8 | 检查成片 | 完整视频、技术检查、音频和交付状态 | 否，本轮只读展示已有结果 |
| 9 | 确认交付 | 可下载文件、版本和发布前检查结果 | 本轮只读展示已有结果 |

三个确认点是固定业务门：

```text
确认脚本 → 确认制作准备 → 查看样片并确认效果
```

“看创意方案”和“看分镜”是可读产物，不新增审批次数。第 7–9 步属于完整生产线的后半程，本轮只实现“选中 1–2 条并写入精剪队列”；已有成片和交付结果可以只读查看，但不新增编辑、成片审批或发布动作。因此本轮仍只有三个可执行的人审门。

### 2.2 产物如何呈现

每一步都只回答“看什么、判断什么、之后发生什么”。产物按以下顺序呈现：

| 产物 | 一线标题 | 首屏内容 | 展开后内容 |
|---|---|---|---|
| 研究与素材体检 | 任务理解 | 参考片重点、现有素材是否够用、风险提示 | 参考片片段、素材清单、匹配依据 |
| 创意方案 | 创意方向 | 方向名称、开头方式、核心卖点、差异说明 | 方案对比、适用平台和时长 |
| 脚本 | 制作脚本 | 逐段口播、屏幕文字、时长合计 | 语音/字幕对齐和超时提示 |
| 分镜 | 镜头安排 | 镜头顺序、画面、动作、时长 | 原素材时间段、取景和转场说明 |
| 制作准备 | 生成清单 | 口播、字幕、背景音乐、画面素材、预计费用 | 音轨状态、素材计划、生产设置 |
| 样片 | 样片预览 | 视频播放器、总分、推荐结论、风险 | 五项确认、评分细项、样片报告 |
| 成片 | 完整视频 | 播放器、检查结论、版本和下载 | 技术检查、音频检查、交付证书 |

技术字段（例如项目路径、模型、渲染引擎、哈希和事件编号）统一放进“制作记录”折叠区。页面正文不得出现内部英文枚举、`undefined`、文件路径或“打开 JSON”。

## 3. 批量与单条的串联

### 3.1 两个视图，不是两套流程

批量台和单条台共享同一批事实：批次索引、候选项目、候选 revision、审批记录、检查结果、成本和事件。区别只有信息密度和操作范围：

| 视图 | 适合做什么 | 主操作范围 | 事实来源 |
|---|---|---|---|
| 批量总览 | 横向比较、批量确认、选择候选 | 多个候选 | 批次聚合投影 + 候选快照 |
| 单条复核 | 播放视频、逐项看产物、单独通过或退回 | 一个候选 | 候选项目原始审批事实 |

单条页面不是批量页面的复制品。批量台负责“选谁、批量确认什么”，单条台负责“这一条是否真的可以通过”。

### 3.2 进入和返回

批量候选卡提供两个入口：

- “快速查看”：在批量台右侧打开只读抽屉，滚动位置和已选候选不变；抽屉只展示视频、结论和当前产物，不提供通过、退回或选择动作；
- “打开单条复核”：进入同源的 `/p/<candidate-id>?from=batch&batch_id=<batch-id>` 页面，适合需要完整阅读脚本、分镜和样片的人。

单条页面顶部固定显示：

```text
批次名称 / 候选名称       [返回批量总览]
当前确认：样片效果        [仅通过这一条]
```

返回批量时必须恢复：

- 原批次地址和滚动位置（浏览器支持时）；
- 已勾选候选；
- 当前批次 revision；
- 已完成的单条确认结果；
- 批量主动作的可用/不可用状态。

导航状态用 `candidate_id + subject_hash` 绑定用户看过的内容，不使用会因审批状态变化而改变的 `child_revision`。单条“通过这一条”只改变 review/checkpoint，若 `subject_hash` 未变，返回批量后保留勾选并刷新状态；只有视频、脚本、制作清单或样片内容变化导致 `subject_hash` 变化，或候选不再具备当前动作资格时，才显示“这条视频有新版本，请重新看一遍”并清除该候选勾选。

`aggregate_revision` 只用于批量命令的乐观并发。它变化时页面先重新拉取，而不是无条件清空所有本地选择；刷新后逐候选按 `subject_hash + eligibility` 对账。多标签页中，较旧页面提交会得到 `stale`，不能覆盖较新页面结果。

### 3.3 当前门、混合阶段和候选资格

批次允许候选处在不同阶段。页面按固定顺序 `脚本 → 制作准备 → 样片` 选择“最早仍有待确认候选的门”作为唯一当前门：

1. 已经单条通过该门的候选不再进入批量参与者列表，但仍显示“已通过”；
2. 尚未到达该门的候选显示“制作中”，不可勾选；
3. 已进入更后阶段的候选不回退，也不参与当前门；
4. 被退回、技术失败、缺失或损坏的候选不参与批量通过，但保留在画廊；
5. 当前门没有待确认候选后，页面重新归约并显示下一个门或选择阶段。

候选在样片阶段的业务状态和后续行为如下：

| 状态 | 是否参与当前批量通过 | 是否可进入精剪选择 | 是否阻塞其他候选 |
|---|---|---|---|
| `awaiting_review` 待确认 | 是 | 否 | 否 |
| `approved` 已通过 | 否 | 完成评分且报告完整后可选 | 否 |
| `needs_revision` 已退回 | 否 | 否 | 否 |
| `failed` 技术失败 | 否 | 否 | 否 |
| `artifact_health=missing/corrupt` 产物异常 | 否 | 否 | 否 |
| `excluded` 本轮不参与 | 否 | 否 | 否 |

当所有“存活候选”都已完成样片门和评分，或进入 `needs_revision/failed/excluded` 审核终态，或 `artifact_health=missing/corrupt` 时，批次结束等待并计算可选集合。至少有 1 条 `approved + evaluated + report_complete` 候选时进入选择；没有合格候选时进入“本批没有可用视频”，主动作改为“查看问题汇总”，不显示选择托盘。

“退回并说明原因”在本轮写入 `needs_revision`、结构化问题标签和用户说明，页面显示“已退回，等待制作人员更新”。实际修改可由现有制作流程或后续编辑工作室完成；新内容以新的 `subject_hash` 重新进入对应确认门，旧审批不继承。退回不会卡住其他候选的批量确认或选择。

### 3.4 批量审批的两步

“批量两步”是批量台的操作结构，不会减少三个生产确认点：

**第一步：批量确认当前待确认内容**

页面只显示当前正在等待的门。例如当前是“确认样片”，候选卡显示样片和结论，右侧显示五项效果检查。用户可以先打开一条深入复核，再勾选要纳入批量动作的候选，最后点击“通过已勾选的 4 条样片”。

**第二步：批量选择进入精剪并统一提交**

所有存活候选完成样片门和评分后，用户从合格候选中选择 1–2 条，托盘显示“已选 2 / 最多 2”，点击“提交这 2 条进入精剪”。未通过样片、未完成评分、报告不完整或处于失败/退回状态的候选不可选择。本轮只写入选择结果和下一阶段状态，不打开编辑工作室。

每次批量动作都由协调记录包住，但每个候选仍写入自己的 review、decision log 和 checkpoint；批量台不复制或合并单条审批历史。

### 3.5 主流程时序

```text
系统生成候选
  ↓
批量总览：看画面、结论、阶段和风险
  ↓（需要时）
单条复核：播放样片，查看脚本/分镜/制作清单/检查项
  ↓
返回批量：保留上下文，重新校验候选 revision
  ↓
批量确认当前门（脚本 / 制作准备 / 样片）
  ↓
全部候选完成评分
  ↓
选择 1–2 条进入精剪并统一提交
  ↓
后续编辑工作室处理局部修改，完成后回到单条成片复核（不在本轮实现）
```

本轮不实现“修改并重跑”、渲染引擎切换、候选编辑器和批量重跑。退回候选只显示“等待制作人员更新”，不能展示一个当前不可用的编辑按钮。

## 4. 页面结构与交互语言

### 4.1 批量总览

```text
┌──────────────────────────────────────────────────────────────┐
│ 批次名称  当前进度  已完成/总数  预算  待我处理                │
├──────────────────────────────────────┬───────────────────────┤
│ 候选画廊                              │ 当前要做               │
│ 视频画面 + 方向 + 结论 + 证据标签      │ 通过已勾选的样片         │
│                                      │ 待处理候选列表          │
│                                      │ 报告完整性与风险        │
└──────────────────────────────────────┴───────────────────────┘
```

候选卡固定显示：真实视频帧或样片、方向名称、结论、最多 3 个证据标签、成本和当前流程位置。失败候选保留在原位置，显示“样片未生成”或真实失败原因，不用空白卡或假封面代替。

决策栏始终只有一个高强调主按钮，按钮文案带结果和数量：

| 当前情况 | 主按钮 |
|---|---|
| 等待脚本确认 | 通过已勾选的脚本 |
| 等待制作准备确认 | 通过已勾选的制作准备 |
| 等待样片确认 | 通过已勾选的样片 |
| 等待选择 | 提交 1–2 条进入精剪 |
| 没有待办 | 查看当前进度 |
| 报告不完整或快照过期 | 重新拉取最新结果 |

### 4.2 单条复核

单条页面顺序固定为：

1. 批次来源、候选名称、当前结论和返回批量；
2. 视频播放器，默认展示当前需要确认的样片或成片；
3. 九步进度带，当前步骤使用“正在处理 / 等待确认 / 已完成 / 处理失败”；
4. 当前产物卡，例如“制作脚本”“镜头安排”“制作清单”“样片效果”；
5. 当前确认项和通过/退回动作；
6. 制作记录折叠区，放成本、重试、版本和技术信息。

确认动作使用一线语言：

- `通过这一条`：只处理当前候选；通过原因由系统记录为“人工确认通过”，无需额外输入；
- `退回并说明原因`：打开原因输入，不要求选择内部阶段；
- `返回批量总览`：回到批次比较和统一提交；
- `重新拉取最新结果`：当 revision 或报告不一致时使用。

### 4.3 样片五项确认

样片门固定使用以下文字和顺序：

1. 创意方向对不对；
2. 开头是否马上抓住人；
3. 产品/主题证明是否清楚；
4. 节奏和画面是否顺；
5. 字幕是否看得清。

每项只能选择“通过 / 需要修改 / 不通过”。五项选择按 `review_id + subject_hash` 存储；单条页已经对同一 `subject_hash` 完成的五项可以在批量动作中复用，内容变化后必须重新确认。只有五项都是“通过”时，候选才可进入批量通过；“需要修改”和“不通过”必须留在候选状态中，并显示原因。

## 5. 状态、数据和一致性

### 5.1 展示模型

现有 `batch_review.data` 继续作为只读展示输入，新增或规范以下字段：

| 字段 | 用途 | 业务文案 |
|---|---|---|
| `batch_id` | 批次身份 | 批次 |
| `aggregate_revision` | 批量动作快照 | 批次结果版本 |
| `candidate.subject_hash` | 单条内容快照；内容不变则稳定；已有可审产物时必填 | 这条视频版本 |
| `candidate.workflow_revision` | 审批/checkpoint 乐观并发 | 不直接展示 |
| `candidate.preview_url` | 样片/成片预览 | 视频 |
| `candidate.current_step` | 当前阶段 | 当前步骤 |
| `candidate.current_artifact` | 当前产物 | 正在看的内容 |
| `candidate.review_status` | 单条审核状态 | 待确认/已通过/需修改 |
| `candidate.artifact_health` | 产物是否可用 | 正常/缺失/损坏/播放失败 |
| `pending_gates` | 批量待确认门 | 当前要做 |
| `selection` | 精剪选择 | 已选/最多 |
| `reports.data_quality` | 报告可用性 | 结果是否完整 |

内部阶段仍保留稳定 ID，但由 `backlot/operator_language.py` 统一映射为业务文案。UI 不根据候选数量或评分自行猜测阶段和资格。

本轮将 `batch_review` 展示 schema 升为 `1.1`。新增字段由 `backlot/batch_state.py` 从候选事实确定性派生，前端只消费，不回写：

```json
{
  "candidate_id": "string, required",
  "project_id": "string, required",
  "subject_hash": "64-hex; 已有脚本、制作清单或样片时必填，尚未产生内容时可为 null",
  "workflow_revision": "integer >= 0",
  "current_step": "research|proposal|script|scene_plan|assets|sample|edit|compose|publish",
  "current_artifact": "research|proposal|script|scene_plan|production_plan|sample|final|delivery|none",
  "review_status": "not_ready|awaiting_review|approved|needs_revision|failed|excluded",
  "artifact_health": "ready|missing|corrupt|playback_failed|unknown",
  "preview_url": "same-origin URL | null",
  "selection_eligible": "boolean",
  "selection_block_reason": "string | null"
}
```

`subject_hash` 由当前或最近一次已决 review 绑定的内容产生，review 关闭后仍保留；样片评分则额外绑定 `evaluation_hash`。只有候选尚未产生任何可审内容时才允许为 `null`，此时 `review_status=not_ready` 且不可选择。`workflow_revision` 由候选审批/checkpoint generation 产生，`artifact_health` 独立表达 `missing/corrupt/playback_failed`，不挤占审核状态；`selection_eligible` 只能由服务端按 §3.3 计算。字段缺失、类型错误或枚举未知时 schema 校验失败；历史批次由投影层返回明确的 `not_ready/unknown`，前端不自行补猜。schema `1.0` 客户端只读兼容，写动作必须先重新拉取 `1.1` 快照。

### 5.2 批量动作合同

批量确认和批量选择都必须提交：

- 批次 `aggregate_revision`；
- 每个候选的 `candidate_id`、`project_id`、`review_id`、`workflow_revision`、`subject_hash`；
- 样片门的五项确认（仅样片门）；
- 幂等键和用户原因。

服务端先执行 prepare：核对权限、候选归属、内容 `subject_hash`、流程 `workflow_revision`、确认项和报告完整性；全部通过后再 commit。跨项目不能依赖一个数据库事务，因此协调器按稳定的 `project_id` 顺序加锁，把每个候选的 review、checkpoint、approval bundle、decision log 和 outbox 事件写入 prepared generation，再统一提交 current pointer。批量投影有 `visibility_fence`：只要 coordinator 不是 `committed/replayed`，批根和候选投影都继续读取旧 current pointer，并隐藏 prepared generation；事件 outbox 也只在 fence 放行后发布。任一候选在 prepare 失败，清理所有 prepared generation 并返回 `stale`、`forbidden` 或 `validation_failed`，不产生用户可见批准。

commit 中途进程退出时，协调记录保持 `committing` 和每个参与者的 commit marker。恢复器按原顺序继续提交；每次 pointer 更新使用“旧 generation + coordinator id”条件写入，发现参与者内容或流程版本已被外部改变时转为 `needs_recovery`，不覆盖新事实。由于 visibility fence 尚未放行，已切换的 pointer 不会被用户看到；无法继续时只对仍匹配 coordinator marker 的参与者执行 CAS 补偿回滚，无法安全回滚则保留旧可见版本并等待人工恢复，不做静默覆盖。只有全部 marker 齐全后才切换 fence、释放 outbox 并返回 `committed`；重复请求按批次作用域的幂等键返回 `replayed`。

批量命令的最小请求合同如下：

```json
{
  "action_type": "batch_approve_gate",
  "gate": "sample",
  "aggregate_revision": "<64-hex>",
  "reason": "批量确认样片",
  "participants": [{
    "candidate_id": "direction-a",
    "project_id": "candidate-a",
    "review_id": "review-a",
    "subject_hash": "<64-hex>",
    "workflow_revision": 4,
    "effect_confirmations": {
      "creative_direction": "pass", "hook": "pass", "proof": "pass",
      "pacing": "pass", "readability": "pass"
    }
  }]
}
```

成功响应为 `{status:"committed", batch_action_id, aggregate_revision, participants:[...]}`。失败响应必须包含 `{status, batch_action_id, participant_errors:[{candidate_id, code, message, retryable}], current_revisions, retryable}`。`Idempotency-Key` 只放请求头，不放 body；服务端把 header 值写入 coordinator record，缺失或为空直接拒绝。批量确认原因默认使用“批量确认当前门”，批量选择原因使用用户填写的选择理由；两者都写入审计，不要求一线人员填写内部字段。

批量选择继续使用 `POST /api/v2/projects/{batch_id}/batch/select`，请求为 `{action_type:"batch_select_for_edit", aggregate_revision, participants:[{candidate_id, project_id, subject_hash, workflow_revision, evaluation_hash}], reason}`；服务端重新验证候选归属、`selection_eligible` 和报告 hash，并把 `candidate_ids` 从 participants 确定性派生。两个批量端点都要求 `Idempotency-Key` 请求头；作用域为批项目，至少保留到该 coordinator record 被归档。同 key 同请求返回 `replayed`，同 key 不同请求返回 `idempotency_conflict`。

### 5.3 单条与批量事实边界

- 单条通过：直接调用现有候选审批服务，写入候选自己的审批事实；
- 批量通过：由批量协调器让同一审批服务写入 staged sink，全部 prepare 成功后再推进各候选 generation pointer；不能在普通循环中逐个直接提交；
- 批量选择：写入批次选择结果，候选 `candidate_id` 不变；
- 批量总览：只读聚合，不在读取时创建 review、补事件或修改 checkpoint；
- 单条页面：显示事实，不复制批次状态；需要返回批量时只携带导航上下文。

## 6. 视觉方向

采用克制的编辑室式语言，让视频画面成为主角：温暖浅底、黑色正文、灰色结构线、绿色通过、赭色重点、珊瑚色风险。避免品牌词、技术控制台风格、紫色渐变、霓虹光晕和大面积纯黑。

- 批量画廊使用固定 16:9 媒体容器，先画面后结论；
- 单条页面使用“播放器 + 产物卡 + 确认项”纵向阅读，不把技术信息铺满首屏；
- 卡片圆角不超过 8px，状态颜色必须同时配文字；
- 移动端候选一列，底部操作条为内容预留空间；
- 播放、关闭、返回等熟悉操作使用图标并提供中文无障碍名称；
- 页面标题、按钮和提示全部采用业务中文，不显示产品品牌或内部项目代号。

## 7. 验收场景

### 场景 A：批量比较到单条复核

1. 打开批量总览，首屏看到 5 个候选、当前确认门和唯一主按钮；
2. 点击“结果先行”候选，右侧抽屉出现真实视频、九步进度、制作脚本和样片效果；
3. 点击“打开单条复核”，页面顶部显示批次来源和“返回批量总览”；
4. 单条审批只改变流程状态且 `subject_hash` 未变化时，返回后原候选仍被选中；
5. 模拟候选内容 `subject_hash` 变化，返回后显示需要重新确认并只清除该候选勾选。

### 场景 B：批量样片确认

1. 决策栏显示“通过已勾选的样片”；
2. 用户取消一个风险候选，其余候选仍可批量通过；
3. 任一候选五项确认不是“通过”，prepare 阶段拒绝整批；
4. commit 成功后每个候选都有自己的审批记录，批次显示“已进入人工选择”；
5. 重复点击返回原结果，不新增审批记录。

### 场景 C：批量选择进入精剪

1. 所有存活候选已完成评分或进入终态，且至少一条合格候选报告完整时显示选择托盘；
2. 选择超过 2 条时即时阻止并说明“最多选择 2 条”；
3. 提交后批次记录选中候选和理由，候选页面可从批次返回；
4. 本轮不出现编辑器或“修改并重跑”按钮。

### 场景 D：失败和降级

1. 技术失败候选仍显示真实 poster 或“样片未生成”；
2. 报告缺失、事件缺口、快照过期时，主按钮变为“重新拉取最新结果”；
3. 用户能看到失败原因和下一步，不会看到“已通过”或空白状态。

### 场景 E：混合阶段、退回和无合格候选

1. 候选分别停在脚本、制作准备、样片时，批量台只显示最早待确认门；尚未到门的候选不可勾选，已单条通过的候选显示“已通过”；
2. 候选退回后进入“等待制作人员更新”，不阻塞其他候选的批量确认；新版本必须以新的 `subject_hash` 重新确认；
3. 所有候选都失败、缺失、损坏或退回时显示“本批没有可用视频”和问题汇总，不显示进入精剪；
4. 只有已通过样片、完成评分且报告完整的候选可进入选择托盘。

### 场景 F：原子提交、并发和权限

1. prepare 阶段任一候选 stale、无权限或确认不完整，所有候选保持原状态；
2. commit 中途故障后，恢复器能续跑或补偿回滚；恢复期间页面显示“需要恢复这次提交”；
3. 同一幂等键和同一请求返回原结果，不重复审批；同一幂等键对应不同请求返回“这次提交编号已被占用”；
4. 单条审批后只更新流程状态时保留批量勾选；内容 hash 变化时要求重新看；多标签页旧快照得到“结果有更新，请重新拉取”。

### 场景 G：直接访问和媒体异常

1. 直接打开没有批次参数的单条页面，不显示返回批量按钮；
2. 批次与候选不匹配、候选被删除或归档时，显示“候选已不可用”，不允许审批；
3. 预览地址失效、播放失败或刷新超时，保留产物文字和“重新拉取最新结果”，不显示假封面；
4. 权限在加载后被收回时，提交返回 `forbidden` 并刷新权限状态。

## 8. 非目标与后续

本轮不做：

- 编辑工作室、局部修改、修改并重跑；
- 批量生成调度器和新的生成模型；
- 替换现有审批后端事实存储；
- 新增品牌命名或把技术字段改成一线必读信息。

后续编辑工作室接入时，必须从单条复核入口进入，并在完成新版样片后回到同一条单条确认，再回到批量总览；不能另建一套审批状态。
