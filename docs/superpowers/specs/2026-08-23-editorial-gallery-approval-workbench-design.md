# Editorial Gallery 批量审批工作台设计

> 日期：2026-08-23  
> 状态：设计规范与高保真 mockup 已验证；生产接入仍受契约 review 阻塞
> 适用入口：`/p/<batch-id>`  颁发给：批量混剪运营与内容负责人

## 1. 设计目标

OpenMontage 的批量审批工作台需要同时服务两种人：每天处理多个候选的运营人员，以及需要判断创意与成片质量的内容/品牌负责人。当前页面的问题不是信息不足，而是所有信息都以同等优先级平铺：预算、阶段、门审批、评分、音轨、成本和失败原因彼此竞争注意力，用户无法快速回答“现在最该做什么”和“哪一个候选值得继续”。

本设计把工作台定义为 **Editorial Gallery（编辑室画廊）**：

- 画廊承担视觉判断：真实样片帧、方向摘要和一眼可读的质量结论。
- 决策栏承担流程推进：当前唯一主动作、待处理数量、审批/选择状态。
- 复核抽屉承担证据核验：完整预览、五项样片确认、评分细项、音轨、成本与失败日志。
- 技术状态仍可追溯，但不占据首屏主叙事。

### 成功标准

1. 用户打开批页后 5 秒内能回答：批次处于什么阶段、需要我做什么、哪些候选值得看。
2. 用户不打开抽屉即可完成常见批量审批和 1–2 个候选选择。
3. 用户打开任一候选抽屉后，不离开批页即可完成深度复核并回到原选择上下文。
4. 画面是决策的一等信息：样片预览不能被状态芯片、技术字段或装饰性 UI 压缩成无意义缩略图。
5. 失败候选保留可见、可解释、可追溯，不因视觉降级而被误认为不存在。
6. 当报告或候选快照不新鲜时，用户能明确知道“为什么不能操作”和“下一步如何收敛”，而不是面对静默禁用按钮。mockup 的浏览器验收通过，但不等同于生产契约已闭合。

## 2. 信息架构

### 2.1 页面骨架

```text
┌──────────────────────────────────────────────────────────────┐
│ 批次指挥条：名称 / 阶段 / 完成度 / 预算 / 待处理               │
├───────────────────────────────┬──────────────────────────────┤
│                               │                              │
│  候选画廊                     │  决策栏                      │
│  真实样片卡 × N                │  当前唯一主动作              │
│  画面 + 结论 + 证据条           │  待审批列表 / 选择托盘         │
│                               │  风险与下一步                 │
│                               │                              │
└───────────────────────────────┴──────────────────────────────┘

点击候选卡：右侧打开深度复核抽屉，不改变主视图滚动位置。
```

页面不再把 6 相批级轨道作为左侧永久导航。轨道缩为顶部一条轻量阶段线；点击阶段只显示该阶段的筛选/说明，不切换成另一套工作台。

### 2.2 顶部批次指挥条

从左到右显示：

1. 批次标题与来源素材池。
2. 当前阶段标签，例如「样片评估」。
3. 完成度：`3/5 已完成`，必要时补一句「1 个候选需返工」。
4. 预算：`$8.20 / $30.00`，预算超限使用明确警示而非仅换颜色。
5. 待我处理：`4 项`，作为视觉焦点之一。

不在顶部显示 provider、model、runtime、generation id 等技术字段；这些只在复核抽屉的“制作证据”区域出现。

### 2.3 候选画廊

默认按“可决策程度”排序：`推荐` → `可选` → `待评分` → `需返工` → `技术失败`。用户可以切换为“评分最高”“最近更新”“原始方向顺序”。

每张候选卡是一个独立的媒体容器，但页面不再嵌套卡片。卡片结构固定为：

```text
┌────────────────────────────────┐
│ 真实视频帧 / 3 秒预览            │  ← 主视觉，占卡片约 56%
│                                │
├────────────────────────────────┤
│ 结果先行                 8.4    │  ← 方向 + 总结论
│ 先展示最终效果，再补证据          │  ← 一句创意摘要
├────────────────────────────────┤
│ 推荐 · 口播清晰 · 音乐匹配        │  ← 最多 3 个证据标签
│ $1.46 · 样片确认 · 5 / 9          │  ← 次级状态
└────────────────────────────────┘
```

卡片首屏只承载 6 类信息：预览、方向、摘要、总分/结论、最多 3 个证据标签、成本/阶段。完整 8 维评分、三轨音频、失败栈和 revision 放入抽屉。

### 2.4 决策栏

决策栏是固定宽度的流程锚点，内容根据批级 phase 和 pending gates 动态变化。它只能有一个高强调主按钮：

| 情况 | 主动作 | 辅助内容 |
|---|---|---|
| script gate | 批量通过剧本 | 待确认候选列表、查看详情 |
| assets gate | 批量通过素材 | 付费调用提示、候选列表 |
| sample gate | 批量通过样片 | 五项确认完成度、被排除候选 |
| selection phase | 进入精剪 | 选择托盘 `0/2`、排序提示 |
| editing/publishing | 查看选中候选 | 选中候选、交付状态 |
| 无待办 | 等待系统推进 | 当前阶段、预算和异常 |

主按钮必须带动作结果预告，例如「通过 4 个样片并进入评分」。不使用“提交”“确认”这类没有结果含义的泛化文案。

### 2.5 深度复核抽屉

抽屉宽度桌面端 `min(520px, 42vw)`，移动端为全屏。结构顺序：

1. 候选标题、方向、结论和关闭按钮。
2. 完整样片播放器，默认从 0 秒开始，支持循环前 3 秒。
3. 证据摘要：L1a 状态、L3 评分、关键优点/风险。
4. 样片门的五项确认，只有全部完成且均为 pass 才允许通过。
5. 三轨音频状态：口播、BGM、原声；只显示状态和播放控制，不展示内部文件路径。
6. 成本、重试、provider/model/runtime、失败原因和 revision，置于“制作证据”折叠区。
7. 底部固定候选级动作：`通过此候选`、`要求返工`、`打开候选工作台`。

抽屉打开期间，主画廊保持可见但降低对比度；按 Escape、点击遮罩或关闭按钮返回。切换候选时复用同一抽屉，不重建页面上下文。

### 2.6 候选执行进度与局部修改

质量信息必须和候选的九阶段执行进度同时出现，但两者不混为一个指标。抽屉在播放器下方显示候选级阶段带：`research`、`proposal`、`script`、`scene_plan`、`assets`、`sample`、`edit`、`compose`、`publish`。阶段带只回答“做到哪一步、当前卡在哪里”；质量判断回答“当前产物是否值得继续”。

用户点击「修改并重跑」后，工作台不要求用户手动选择起始阶段。用户只需选择修改意图，系统根据当前 `child_revision`、阶段状态和产物依赖图计算最小安全路径：

| 修改意图 | 默认起点 | 最小路径 |
|---|---|---|
| 节奏与镜头 | `edit` | `edit → compose` |
| 口播与字幕 | `script` | `script → scene_plan → assets → sample → edit → compose` |
| 画面与素材 | `assets` | `assets → sample → edit → compose` |
| 技术修复 | 失败阶段 | 只重试失败阶段 |

修改入口采用「定位 → 描述 → 复述」：用户先点选播放器时间段、镜头/质量维度或失败阶段，再选择修改类型并补充一句「位置 + 问题 + 目标」的自然语言。系统在路径确认前显示「已理解」摘要；摘要缺少目标时只追问一个最小澄清项，不要求用户理解内部 stage id。

VLM 低分项作为建议范围出现在修改入口的第一层：每项包含评分、证据定位和建议动作。用户勾选要处理的低分项后，系统生成可编辑草稿；计划面板分别标记 VLM 建议范围与用户补充范围。多个建议按依赖闭包并集计算，VLM 不直接触发重跑；最终仍需用户确认范围。

确认面板必须展示：起始阶段、将重跑的阶段、会保留的阶段、预计成本、新 revision，以及“旧版审批不会继承”的提示。确认后创建独立 `rerun_run`，候选 `candidate_id` 不变，旧版本继续作为当前版；运行先进入预览门，再由用户决定是否完整重跑。状态依次为 `preview_running → awaiting_preview_review → full_running → awaiting_final_review → promoted/discarded`。预览和完整成片均必须提供前后版本对比、预计质量变化、本次预期变化和“保留当前版”出口。如果规划期间 revision 变化，动作返回 `stale` 并要求重新规划，不得覆盖新版本。

渲染引擎支持 Remotion 与 HyperFrames。两者都可用时，proposal 阶段必须展示各自适用场景和权衡，用户确认后锁定 `render_runtime`。局部重跑默认沿用锁定值；主动切换引擎必须作为高影响决策重新确认、重算成本与预期，并追加 `render_runtime_selection` decision revision，不允许失败后静默 fallback。

### 2.7 选择托盘

进入 selection phase 后，用户勾选候选不会立即提交。画廊底部出现轻量托盘：

- 左侧显示已选候选缩略图和名称。
- 中间显示 `已选 2 / 最多 2`。
- 右侧只有一个主按钮「进入精剪」。
- 选择超过 2 个时，第三个选择被阻止并解释上限；不在提交后才报错。

### 2.8 批级差异与报告带

画廊下方放置一条横向“差异与效率”带，默认只露出三个决策指标：`结构差异覆盖`、`报告新鲜度`、`选择阻塞`。点击后展开完整矩阵和两份报告摘要。这样“审美判断”仍由画面和一句结论承载，“决策直觉”则由差异证据和可操作阻塞项承载，避免把报告做成第二个技术面板。

差异矩阵单元格展示：`3 个结构差异镜头`、`结构通过/同质化`、`视觉相似度低/高风险`；缺少变体计划展示“证据缺失”。运行报告摘要展示总耗时、最慢阶段、人工等待、重试率、缓存命中率和总成本；质量报告摘要展示 L1a/技术 QA、VLM、五项人工确认、返工次数和下一步建议。两份摘要都显示 `generated_at`、`report_revision`、`semantic_sha256` 前 8 位和 `data_quality`。

当 `data_quality` 为 `partial`/`degraded`/`missing`、报告输入 hash 与 `aggregate_revision` 不匹配或事件序列有缺口时，动作栏进入只读降级：保留「查看证据」「重新拉取报告」，禁用「批量通过」与「进入精剪」，并说明阻塞来源。mockup 通过 `?outcome=stale|forbidden|validation_failed|needs_recovery|replayed` 回放跨项目动作结果，默认状态仍从 partial 开始。

### 2.9 批级审批的一致性反馈

批级按钮点击后进入 `preparing → prepared → committing → committed` 的轻量状态反馈；失败显示 `stale`、`validation_failed`、`forbidden` 或 `needs_recovery` 的业务文案与候选清单。mockup 使用 fake adapter 模拟这些结果，真实接入必须提交批 `aggregate_revision` 和每个候选的 review snapshot，任一参与者失败都不能留下部分批准。

## 3. 视觉规范

### 3.1 气质

关键词：**编辑室、克制、内容优先、温暖、可靠**。

它不是技术控制台，也不是营销落地页。视觉应让真实样片成为内容主体，同时用有节奏的留白、细线和明确层级建立秩序。

### 3.2 色彩令牌

```css
--canvas: #F3F0EA;       /* 温暖纸张底 */
--surface: #FCFBF8;      /* 内容表面 */
--ink: #202322;          /* 主文字 */
--muted: #77736C;        /* 辅助文字 */
--line: #DCD8D0;         /* 结构线 */
--sage: #55796B;         /* 通过/可继续 */
--sage-soft: #E7EEE9;
--coral: #B85C4A;        /* 返工/风险 */
--coral-soft: #F3E4DF;
--ochre: #A87935;        /* 推荐/重点 */
--ochre-soft: #F2E9D9;
--blue: #416B87;         /* 链接/信息 */
```

禁止使用紫色渐变、霓虹 glow、纯黑大面积背景和装饰性彩色圆点。状态颜色必须同时配合文字，不得只靠颜色表达。

### 3.3 字体与排版

- 中文正文优先 `Noto Sans SC`，回退到系统中文字体。
- 标题使用同一字体的较重字重，不引入夸张 display 字体，避免与真实视频画面争夺注意力。
- 页面标题 28–32px；区域标题 15–18px；正文 13–15px；标签 11–12px。
- 文字不使用负字距；中文标题采用 `text-wrap: pretty`。
- 所有数值和阶段状态使用 tabular figures，保证扫描时列对齐。

### 3.4 媒体规则

- 候选卡媒体比例固定为 `16 / 9`，不得因加载、标签或文本长度改变卡片高度。
- 预览帧必须使用真实本地/项目媒体；无媒体时显示明确的“样片尚未生成”，不伪造渐变封面。
- 播放按钮使用熟悉的播放符号，带 `aria-label`；不要用文字按钮替代已有符号。
- 失败候选保持原始画面或真实 poster，降低饱和度但不隐藏内容。

## 4. 交互与状态规范

### 4.1 交互原则

1. **结论先于证据**：卡片先给判断，抽屉再给依据。
2. **一个主动作**：页面任意状态最多一个高强调动作。
3. **不跳上下文**：候选深审使用抽屉，不跳转新页面。
4. **批量动作可解释**：按钮文案说明影响数量和下一阶段。
5. **失败可理解**：失败候选显示“发生了什么”和“下一步能做什么”。

### 4.2 键盘与可访问性

- Tab 顺序：顶部主导航 → 画廊卡片 → 决策栏主动作 → 选择托盘 → 抽屉内部。
- 抽屉打开后焦点移到标题，关闭后焦点返回触发卡片。
- Escape 关闭抽屉；Space/Enter 激活卡片和按钮。
- 状态标签必须有文字；对比度满足 WCAG AA。
- 播放器、选择框、主按钮均有可读的中文 `aria-label`。

### 4.3 响应式

- `>= 1180px`：画廊 3 列，决策栏 300px。
- `760–1179px`：画廊 2 列，决策栏改为顶部横向决策条。
- `< 760px`：画廊 1 列；决策栏固定在底部；抽屉全屏；选择托盘与底部栏合并。
- 移动端固定操作条必须为页面内容预留底部 padding，不能遮挡候选卡。

## 5. 数据映射与范围

本次 mockup 是隔离的 fixture-driven 原型，使用一个本地 adapter 把现有 `batch_review.data` 映射成展示模型；按钮只模拟结果，不调用生产 API。展示模型不能反向成为事实来源。

### 5.1 现有 payload 到展示模型

| 展示内容 | 事实来源 | 规则 |
|---|---|---|
| 阶段 | `data.phase`、`data.phase_reason`、`data.rail` | 不读取不存在的 `phase_label`；中文文案由 UI label map 提供 |
| 候选画面 | `candidate.media.sample_url` | 缺失显示“样片尚未生成”，不伪造封面 |
| 评分 | `candidate.score.weighted_total`、`candidate.score.dimension_scores`、`candidate.score.evaluation` | `evaluation.recommended_action=proceed` 推导可继续，`repair` 推导需返工，`reject` 推导质量失败 |
| 音轨 | `candidate.media.audio_tracks` | 当前只显示轨道状态；真实播放地址出现前不伪造 audio src |
| 成本/重试 | `candidate.cost.cost_usd`、`candidate.cost.attempts` | 批预算以 `data.budget` 的 cost tracker 投影为准 |
| 技术失败 | `candidate.failure.failure`、`candidate.failure.technical`、`candidate_phase` | `missing/corrupt` 显示为异常状态，不从画廊移除 |
| 待审批 | `candidate.pending_reviews[]`、`data.pending_gates[]` | 抽屉中的确认项必须使用五个 canonical keys |
| 可选择候选 | `data.selection.eligible_candidate_ids` | 只有 `phase=selection` 才显示选择托盘；不重新猜测资格 |

`direction`、创意摘要和证据标签目前属于展示 DTO：mockup fixture 可以提供它们；接入生产前必须决定把它们加入 operator schema，或改由 proposal/score artifact 的确定性字段派生，不能在前端凭空生成事实。

### 5.2 真实动作边界

mockup 中的“通过样片”“确认此候选”“要求返工”和“进入精剪”均使用本地 fake action adapter，并覆盖 `committed`、`replayed`、`stale`、`forbidden`、`validation_failed`、`needs_recovery` 的演示结果。它们不调用当前 `/batch/*` 端点。

真实接入前必须完成：

1. 将当前 `renderBatch` 拆分为 `renderBatchHeader`、`renderCandidateGallery`、`renderDecisionRail`、`renderCandidateDrawer`、`renderSelectionTray`，并同步改造 page shell，移除单任务左侧阶段导航的强制渲染。
2. 批量审批请求携带 `aggregate_revision`、每候选 `review_id/subject_version/subject_hash` 和 sample 五项确认；选择请求携带 evaluation revision/hash。
3. 后端实现 coordinator 的 prepare/commit/recovery 和逐候选权限校验，UI 根据响应状态禁用/恢复主动作。
4. 批级事件接入 `/batch/events`，检测 `event_seq` 缺口后完整补拉，同时保留抽屉和选择托盘上下文。
5. 将候选方向、摘要、推荐级别和证据标签补入 schema 或定义稳定的 artifact 派生规则。

## 6. Mockup 验收标准

- 浏览器直接打开或通过本地静态服务器访问，无需后端数据即可展示完整批页。
- 推荐在仓库根目录使用 `python3 -m http.server 4173`，然后访问 `/design-demos/editorial-gallery/`；这样 mockup 的真实媒体相对路径可用。mockup 也应能在 `file://` 下打开，但媒体加载失败时必须显示诚实的占位状态。
- 桌面端首屏同时看见顶部批次指挥条、至少 3 张候选卡和决策栏。
- 点击候选卡打开抽屉；关闭后保留原滚动位置和选择状态。
- 抽屉同时显示候选九阶段进度与当前质量信息，明确当前质量判断对应的阶段。
- 点击“播放 3 秒”只影响当前候选，不造成布局跳动。
- 进入选择状态后，选择托盘出现；超过 2 个候选时前端即时阻止。
- 点击“修改并重跑”后，系统根据修改意图自动给出最小路径；确认后生成新 revision 并显示“重跑中”。
- 移动端没有横向溢出，底部操作条不遮挡卡片内容。
- 抽屉具备 `role=dialog`、`aria-modal=true`、焦点移入/移出、Escape 关闭和背景滚动锁定。
- mockup 至少覆盖稳定评分、选择托盘、技术失败和一个动作错误提示；真实一致性状态在后续接入测试中覆盖。
- mockup 覆盖结构差异矩阵、报告 partial/degraded、stale/needs_recovery 和协调提交进度。
- mockup 选择托盘只有在报告完整且 coordinator 为 `committed/replayed` 时可提交；候选抽屉的五项确认和技术失败候选不能绕过批级门。
- 视觉上避免紫色渐变、霓虹、过度圆角和“技术字段瀑布”。

## 7. 非目标

- 本阶段不替换真实审批后端、不修改 `ProjectCommitStore`。
- 不在 mockup 中实现真实视频生成、评分计算或跨项目事务。
- 不把画廊做成公共媒体库；它只服务当前批次的决策。
